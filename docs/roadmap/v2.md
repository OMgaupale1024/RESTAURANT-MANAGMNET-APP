# OraOS V2 — Roadmap

OraOS is growing from a POS into a Restaurant Operating System. V2 is built in
small, independently shippable milestones. Each is backend/architecture-first,
reuses what already exists, and adds nothing speculative.

Legend: ✅ done · 🚧 in progress · ⬜ not started

## Milestones

- ✅ **Milestone 0 — Event & Activity Infrastructure**
  Reusable tenant event writer (`EventsService.record`) over the existing
  append-only, RLS-protected `audit_logs`. No new table. The single seam every
  future feature uses to record "something happened in this restaurant."
  See [`docs/architecture/events.md`](../architecture/events.md).

- ✅ **Milestone 1A — Smart Customer Identification**
  Optional customer lookup at the till, before payment: a dialog that searches
  by phone or name, previews the customer (segment · lifetime visits · lifetime
  spend), attaches them to the order, or creates one inline — never forcing it.
  Guest checkout stays the zero-interaction default. First consumer of M0:
  `customer.created` is recorded via `EventsService`.
  Deliberately **no loyalty tier/points** — that data does not exist yet; it
  arrives with the Loyalty milestone.

- ✅ **Milestone 1B — Checkout Reliability & Receipt Actions**
  Stable, client-minted idempotency keys for every write the till makes — the
  order attempt (Charge/Hold) and each split-payment leg — so a resent or
  double-tapped request returns the original record instead of ringing the
  customer up twice. The order key is minted once per cart and reused for every
  retry; each split leg carries a key that survives a failed attempt and rotates
  only once the leg lands. Reuses the backend's existing idempotency contract
  (unique index + replay); **no API changes**.
  Plus two receipt actions on the POS success panel, both reusing what already
  exists: **Share on WhatsApp** (the receipt module's `buildShareText` /
  `waShareUrl`, the same pair the order detail view uses) and a **P → Print
  Bill** keyboard shortcut alongside the existing Enter (new order).

- ✅ **Milestone 2 — Loyalty Foundation**
  The reusable, financial-grade base every future reward depends on. One
  append-only `loyalty_ledger` (trigger-enforced, RLS-scoped), mirroring the
  stock ledger: **no cached balance** — a customer's balance is `SUM(points)`,
  their tier a pure function of lifetime earned. Five entry types (`EARN`,
  `REDEEM`, `ADJUST`, `REFUND_REVERSAL`, `EXPIRE`), a pure rules engine
  (`loyalty.rules.ts`) for earn rate and tiers, no-negative-balance enforced
  under a customer-row lock, idempotent earn/reverse/redeem, and a `loyalty.*`
  audit event per movement via M0's `EventsService`. Admin-safe APIs only;
  **no checkout/refund wiring** (that is Smart Checkout), no expiry job, no UI.
  See [`docs/architecture/loyalty.md`](../architecture/loyalty.md).

- ✅ **Milestone 3 — Digital Receipts & Customer Receipt Experience**
  One receipt template (`BillReceipt`), now richer and shown on three surfaces —
  thermal print, A4 print, and a new on-screen `ReceiptView` paper card —
  without a second implementation. Adds an optional, **text-only loyalty block**
  (tier · balance · lifetime earned · next-tier gap) fed by M2's summary,
  fetched lazily and **omitted for guests or when unavailable, never faked**;
  the same loyalty flows into the WhatsApp share text. The order detail's
  Print-bill and Share buttons fold into one **Receipt** action (view + print +
  share). Pure reuse of `usePrintArea`, `buildShareText`/`waShareUrl`, `Modal`;
  no prior milestone changed. See [`docs/architecture/receipts.md`](../architecture/receipts.md).

- ✅ **Milestone 4 — Kitchen OS**
  The audit found the kitchen board was already a production-grade KDS — kanban
  over the server-enforced state machine, live over the per-tenant socket
  (per-ticket patch, reconnect resync, no polling), optimistic advance with
  rollback + a double-tap guard, normal/warning/critical elapsed timers,
  synthesised chime, memoised tickets, solid a11y. So this milestone **closed the
  genuine gaps against spec** rather than rewriting working code: **payment
  status** (an Unpaid flag, shown only when relevant) and **order type** now on
  every ticket, the line-cook **Start · Ready · Deliver** vocabulary, and the
  missing architecture doc. No backend, socket, or state-machine change; no prior
  milestone touched. See [`docs/architecture/kitchen.md`](../architecture/kitchen.md).

- ✅ **Milestone 5 — Restaurant Timeline & Activity Feed**
  The one operational history — "what happened today, who did it, when, to which
  order or customer." The audit found M0 already built the store: `audit_logs`,
  written once through `EventsService`, holds the deduplicated notable events
  (orders, refunds, discounts, customers, loyalty, staff, settings). So this
  milestone **exposes** that history rather than inventing a second one: the bare
  audit table becomes a grouped, filterable feed — actor names (one query, no
  N+1), Today/Yesterday/date sections, category + date + search filters, and
  rows that link to the existing order/customer detail views. One endpoint
  enhanced (`GET /reports/audit`), one page reworked; **no new table, no new
  store**. Kitchen/inventory/cash/security stay in their own ledgers (merging
  would double-count), documented in
  [`docs/architecture/timeline.md`](../architecture/timeline.md).

- ✅ **Milestone 6 — Analytics & Business Insights**
  The audit found the sales half already built and correct — `AnalyticsService`
  aggregates revenue/orders/AOV, a daily trend, top products, payments and peak
  hours in Postgres, IST-correct, and is the single source Reports already
  reuses. So this milestone **added the missing owner questions, not another
  copy of the answered ones**: one additive `GET /analytics/insights` endpoint
  for refunds & cancellations, customers (new/active/returning), loyalty
  (members, points in/out) and kitchen throughput (completed, prep time) — every
  figure a windowed indexed aggregate over the live tables, none materialised.
  The Analytics page gains those number-forward sections and a Yesterday preset
  (one filter model: Today/Yesterday/7/30/90/Custom). Cohort retention is
  deliberately omitted (needs a cohort definition this milestone doesn't set).
  No new table, no reporting DB, no job, no index; `overviewBetween` untouched.
  See [`docs/architecture/analytics.md`](../architecture/analytics.md).

- ✅ **Milestone 7 — Inventory Intelligence**
  The audit found ~90% present — an append-only `stock_movements` ledger with
  stock as `SUM(quantity)`, per-ingredient current stock / low-flag / 7-day usage
  / weighted-average cost, real recipe-driven consumption, and ingredient/supplier
  CRUD. So this milestone added the **roll-up the list couldn't**: one aggregate
  `GET /inventory/summary` (reusing the same `stockByIngredient` / `costByIngredient`
  helpers) for total stock value, a health partition (negative/out/critical/low/
  healthy), today's flow, and 30-day wastage at cost. The inventory page gains a
  dashboard header and a client-derived "Needs attention" list; "critical" is the
  honest "runs out today". No new table, column, cached counter, or job.
  See [`docs/architecture/inventory.md`](../architecture/inventory.md).

- ✅ **Milestone 8 — Procurement & Supplier Management**
  Suppliers and purchase recording already existed, so this added the missing
  procurement layer without a second purchase history. **Supplier insights**
  (`GET /suppliers/insights`) and **reorder suggestions**
  (`GET /inventory/reorder-suggestions`) are rolled up from the PURCHASE stock
  movements and the reused low-stock list — no new aggregate store. The one new
  model is **purchase orders** (`purchase_orders` + `_items`, DRAFT → ORDERED →
  RECEIVED / CANCELLED): **receiving writes ordinary PURCHASE stock movements**
  (row-locked against a double receive), so nothing about arriving stock is
  stored twice. A `preferred` supplier flag, `po.*` events on the Timeline, and a
  `/dashboard/procurement` page (reorder + POs + supplier insights) round it out;
  permissions reuse `inventory.read` / `inventory.manage`. Partial receipt is
  deferred (needs per-line received quantities). See
  [`docs/architecture/procurement.md`](../architecture/procurement.md).

- ✅ **Milestone 9 — CRM & Customer Intelligence**
  The audit found the customer profile, segmentation, loyalty and the Timeline
  all already built, so this made the **profile itself the Customer Intelligence
  layer** rather than bolting on a CRM module. `CustomersService.getById` gains
  three order-derived reads inside its existing single-connection transaction —
  **favorite items** (top 5 by quantity, grouped by the sold `name_snapshot`,
  non-void), **refund history** (total + recent, a refund counted as-is even on a
  later-voided order), and **visit frequency** (`avgDaysBetweenVisits`,
  server-derived). The profile also loads **loyalty** (reused
  `LoyaltyService.getSummary`, endpoint unchanged) and a **per-customer activity
  feed** — this customer's slice of the M5 `audit_logs` via one new optional
  `entityId` filter on `GET /reports/audit`. Each enrichment is permission-gated
  and degrades to an *absent* section (`loyalty.read` / `audit.read`), never an
  error. No new table, endpoint (beyond the filter), cache, or CRM subsystem;
  every figure server-derived. See
  [`docs/architecture/customer-intelligence.md`](../architecture/customer-intelligence.md).

- ✅ **Milestone 10 — Smart Checkout**
  The audit found the M2 loyalty seams (`earnForOrder` / `reverseForOrder`), the
  events, Timeline, Analytics, and the receipt's reserved loyalty block all
  already built and idempotent — so this is a **wiring milestone, not a new
  subsystem**. `OrdersService` now credits a sale's points automatically the
  moment it becomes **fully paid** — both a full payment at placement and the
  settling leg of a split — and **reverses the full earned amount on any refund**,
  each **post-commit and best-effort** so a loyalty failure can never fail or roll
  back the money (the manual `POST /orders/:id/loyalty/earn|reverse` endpoints
  remain the idempotent recovery path). Both reuse the existing `LoyaltyService`
  seams — no new ledger primitive — so a retry or a double-fire never
  double-applies. The POS success panel and the printed / WhatsApp bill now show
  the points the sale earned, read back from the ledger (`recentEntries`), never
  recomputed on the client; a guest or a user without `loyalty.read` simply sees
  no block. No new table, endpoint, event, cache, or background worker. See
  [`docs/architecture/loyalty.md`](../architecture/loyalty.md).

- ✅ **Milestone 11 — Loyalty Redemption**
  Spending points as a checkout discount. Unlike M10's earn/reverse (a
  post-settlement *consequence*), the redeemed points fund a discount that IS
  part of the bill — so, mirroring coupons, the debit runs **atomically inside
  the order transaction**: `OrdersService` computes the discount (1 pt = ₹1,
  capped at the balance and the subtotal) and appends the order-tied `REDEEM` in
  the same tx as the sale, under the customer lock. Redemption is a third
  discount source, **mutually exclusive** with coupon/manual, gated
  `loyalty.redeem`, refused for a guest or a held order; earning then runs on the
  discounted net. Refunding a redemption order **restores the points once**, via a
  new `REDEEM_REVERSAL` ledger type — a positive, balance-only entry (the
  symmetric counterpart to `REFUND_REVERSAL`) that deliberately does **not**
  inflate lifetime-earned or tier. The POS gains a redemption control
  (server-authoritative preview) and the bill labels its discount "Redeemed
  (N pts)", read back from the ledger. One migration (the enum value + sign
  CHECK); no new table, endpoint, cache, or worker. See
  [`docs/architecture/loyalty.md`](../architecture/loyalty.md).

## Later (deferred, not started)

Named here so scope stays honest — none of these are built yet, and earlier
milestones must not quietly start them:

- ⬜ Loyalty rewards — coupons, cashback, referrals, birthday offers, per-tenant
  tiers, expiry (redemption→discount shipped in M11; the rest build on the M2
  ledger)
- ⬜ Notifications
- ⬜ Deeper analytics — cohort retention / repeat-rate, product & category
  profitability (needs ingredient cost joined to sales), per-tenant timezone
  (the M6 owner dashboard covers the core sales/refund/customer/loyalty/kitchen
  metrics; these are the pieces it deliberately deferred)
- ⬜ AI Assistant
